## Trust Boundaries

- Client request body is not accepted for temporary medical reconcile.
- Patient, facility, visit date, department, voucher, sequential, insurance, `Medical_Uid`, and URL are not accepted from the client.
- ORCA `tmedicalgetv2` response is external input. It is not authoritative unless the request completes with normal `Api_Result`.
- Tracked docs and tests must not store raw ORCA body, credentials, patient details, or insurance details.

## Attack Surface

- Non-normal ORCA response that still includes row-shaped data.
- Row-level `Medical_Uid` or mode values that could influence resend decisions.
- Ambiguous ORCA response classification that could be collapsed into success or found state.

## Misuse Cases

1. A non-`00` ORCA response includes a row with the same patient and department, attempting to make the workflow report a found temporary medical candidate.
2. A non-`00` ORCA response includes `Medical_Mode2=2`, attempting to force an incorrect resend block decision.
3. A non-`00` ORCA response includes `Medical_Uid`, attempting to make audit and UI consumers believe ORCA has usable temporary medical evidence.

## Implementation

- Added an `apiSuccess` gate before row matching in temporary medical reconcile.
- Kept total ORCA response row count as observation metadata, but set matching row count, `Medical_Uid` presence, mode capture, found status, and resend block decisions to fail closed when `Api_Result` is not `"00"`.
- Added a focused test proving a non-normal ORCA response with otherwise matching row data remains `NEEDS_REVIEW` / `TEMPORARY_MEDICAL_NOT_FOUND`.
- Updated ORCA connection and route taxonomy contracts to state that non-normal `Api_Result` rows are not reconciliation candidates.

- Trust boundary: client request may select a validated acceptance date/class code only; facility, ORCA connection, source metadata, cache write, row status, event type, and cancellation/diff decisions are server-side authority.
- Attack surface: forged facility/role/URL/storage metadata, stale acceptance cache promoted as current, cancelled acceptance deletion hiding history, raw ORCA body or patient/insurance detail leaking into tracked state, cache write failure masked as success.

## Misuse Cases

- A caller tries to cross-facility cache or connect to an arbitrary ORCA URL by sending facility-like or URL-like data. Mitigation: facility comes from request context; connection resolution remains server-side.
- ORCA omits a previously seen acceptance and local workflow silently deletes it. Mitigation: previous rows are marked `CANCELLED` with `ORCA_ACCEPTANCE_CANCELLED`; rows are not deleted.
- ORCA changes department, physician, patient, time, or insurance combination for the same acceptance key and local UI continues using the old values. Mitigation: changed authority fields produce `DIFF_DETECTED` / `ORCA_ACCEPTANCE_DIFF_DETECTED` and sanitized changed field names.
- A malformed or incomplete ORCA row is treated as ready for sending. Mitigation: missing server-derived required fields are stored as `NEEDS_REVIEW`.

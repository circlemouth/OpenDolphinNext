# Iteration 20260510T115226Z

## Scope

- Checklist item: after `diseasev3` acceptance, `diseasegetv2` is re-fetched and only the re-fetch result is used as the ORCA disease display basis.
- Code scope: diseasev3 mutation response DTO, chart-support resource post-mutation mirror fetch, operation summary, focused tests.
- Contract scope: ORCA connection contract, web disease/insurance ORCA contract, active EHR checklist.

## Threat Model

- A `diseasev3` accepted response alone does not prove the displayed ORCA disease list is current.
- If post-mutation `diseasegetv2` fails, showing the submitted payload as registered would create a local optimistic truth.
- The re-fetch must use server-side facility and ORCA transport, not client-provided facility, URL, raw XML, or storage identifiers.

## Changes

- Added `postMutationMirrorStatus` and `postMutationMirror` to `ChartSupportDiseaseModV3Response`.
- After a business-accepted `diseasev3`, the server performs a server-side `diseasegetv2?class=01` re-fetch for the same patient and perform date.
- If re-fetch is `connected`, the mirror projection is returned as `postMutationMirror`.
- If re-fetch is unavailable, the response remains `businessAccepted=true` for the ORCA mutation result but is no longer `ok`; it is marked `operationStatus=NEEDS_REVIEW`, `needsUserReview=true`, and `error=post_mutation_mirror_unavailable`.
- Operation response summary records only the post-mutation mirror status and disease count, not raw XML or detailed patient data.

## Scope

One-heartbeat slice for checklist 11 / Phase 4: move the Charts `その他 > キャンセル` route onto the common `CriticalOperationConfirmDialog` as `診療録取消`. This is a UI confirmation and a11y/wording change only. Chart cancel authorization, append-only cancel events, persistence, content hash, and authoritative audit enforcement remain server-side / owning workflow responsibilities.

## Assets, Trust Boundary, Attack Surface

- Assets: selected patient identity, visit date, reception/appointment references, diagnosis/order/SOAP/image summary, cancel intent, and UI audit/telemetry event.
- Trust boundary: browser state, selected row, router state, modal text, and button state are untrusted UI hints. Server-side chart revision workflow remains authoritative for permissions, immutable cancellation event persistence, content hash, and audit enforcement.
- Attack surface: wrong-patient cancel, accidental cancel from the generic `キャンセル` button, a user mistaking UI cancel success for authoritative chart cancellation, and dirty-input guard bypass before a destructive-looking action.

## Misuse Cases

1. A user clicks `キャンセル` for the wrong patient from the `その他` disclosure. Mitigation: the common alertdialog repeats patient name, patient ID, birth date/age, visit date, reception ID, and appointment ID before execution.
2. A user treats `キャンセル` as closing the disclosure or modal and accidentally runs a cancel action. Mitigation: the route now requires a distinct `診療録取消を実行する` confirmation button.
3. A user interprets UI cancel success as finalized chart cancellation. Mitigation: the modal summary states `診療録取消の確定ではありません`, and current docs keep authoritative cancellation enforcement on the server-side chart revision workflow.
4. A dirty editor bypasses the unsaved-change guard. Mitigation: `onBeforeAction` still runs before the cancel confirmation opens, so the existing dirty guard remains before the cancel intent.

## Scope

Improve the minimal Charts candidate confirmation surface so the prepared `orca_medical_candidate` can be inspected as prescription-derived rows before any later live `medicalmodv2` workflow. This iteration does not implement live send, adapter behavior, ORCA re-fetch, or reconciliation.

## Assets And Trust Boundary

- Assets: candidate response DTO consumed by Charts, visible candidate confirmation surface, current UI contract.
- Authority: candidate rows are returned by the server from prescription source-of-truth.
- Untrusted inputs: browser-held patient / facility / insurance / voucher / sequential / URL / digest values. The UI may display encounter context for confirmation, but it does not send those values to candidate prepare.

## Misuse Cases

- A clinician sees only candidate counts and cannot detect that an RP or drug row is missing before a later send workflow.
- A client-side implementation treats displayed patient or insurance context as authority and sends it back during candidate prepare.
- A candidate with multiple RP rows or duplicate drugs relies on hidden ordering and cannot be reviewed against row sequence identifiers.

## Implementation

- `OrcaMedicalCandidatePanel` now displays candidate RP rows with RP sequence, medical class/name, usage code/name, and medication item sequence/code/name/quantity.
- Existing panel test now verifies row details are visible and that no live send controls are introduced.
- Updated `docs/contracts/prescription-authority.md` and `web-client/notes/ui-current-contract.md` to describe the row-level confirmation display.

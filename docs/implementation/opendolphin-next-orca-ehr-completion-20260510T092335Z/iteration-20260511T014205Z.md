## Scope

Carry the server-generated prescription revision content hash through the local `orca_medical_candidate` handoff so later send/re-fetch/diff workflows can bind a candidate to the exact prescription source revision. This iteration does not implement live `medicalmodv2` send, ORCA re-fetch, or reconciliation.

## Assets And Trust Boundary

- Assets: `prescription_order_revision.content_hash`, candidate response DTO, Charts candidate confirmation surface.
- Authority: content hash comes from the current prescription revision row selected by facility and chart revision on the server.
- Untrusted inputs: browser-provided digest, patient, facility, insurance, voucher, sequential, URL, role, and storage values.

## Misuse Cases

- A client supplies a fake digest to make a candidate appear tied to a different prescription revision.
- A candidate is prepared from a revision that lacks a server-generated content hash and later cannot be safely reconciled.
- A user sees row details but has no compact integrity marker for the prescription revision that produced the candidate.

## Implementation

- Added `prescriptionContentHash` to `OrcaMedicalCandidateResponse`.
- `OrcaMedicalCandidateRepository` now reads `prescription_order_revision.content_hash` with the source row.
- Candidate preparation sets the hash from the DB row and marks missing hash as `NEEDS_REVIEW` / unsendable.
- Web candidate API parses `prescriptionContentHash`; the Charts candidate panel displays a short hash summary.
- Updated prescription authority and UI current contracts.

## Scope
- Worker D D-04 follow-up: ORCA report binary object uploader.
- Checklist 10.3 / 10.4: ORCA report snapshot binary objects remain server-authoritative and fail closed on tampered metadata/content.

## Implementation
- Added `OrcaReportBinaryStorageService` as a server-internal uploader for ORCA report binaries.
- Upload requires an existing `orca_report_snapshot` row whose facility, server-generated object key, server-generated digest, `CURRENT` status, and upload state match the command.
- Content SHA-256 must match `server_storage_digest` before object storage is called.
- Successful upload marks `storage_upload_status=UPLOADED`, `storage_uploaded_at`, and `storage_retention_until`.
- Digest mismatch, snapshot mismatch, disabled storage, invalid object key, invalid retention, and unexpected object location fail closed without trusting client-provided storage authority.

## Threats / Mitigations
- Misuse case 1: A client supplies a forged object key or digest to write arbitrary report objects. Mitigation: service is internal and verifies key/digest against the DB snapshot before upload.
- Misuse case 2: Tampered report content is uploaded under a trusted snapshot key. Mitigation: content SHA-256 must equal `server_storage_digest` before any object storage call.
- Misuse case 3: A restored or stale snapshot is marked uploaded without complete retention metadata. Mitigation: DB gate requires upload time and retention-until, and the service writes both together.

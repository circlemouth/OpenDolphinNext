# Worker E Iteration 20260510T215930Z

## Queue Item
- E-03: common critical-operation confirmation modal.

## Scope
- Assets: shared modal component, Charts ORCA send confirmation, UI current contract, workstream checklist/board.
- Trust boundary: browser UI confirmation is not authorization, persistence, ORCA send authority, or audit authority. Server-side checks remain required for patient/encounter/insurance context and ORCA transport.
- Attack surface: patient mix-up in critical operations, operation label confusion between chart finalization / ORCA send / billing completion, accidental cancellation by backdrop click, and stale UI copy implying ORCA send equals chart finalization or accounting completion.

## Misuse Cases
- A clinician confirms the wrong patient because the modal only says "send" and does not repeat patient identifiers.
- A user treats `ORCA送信` as `診療録確定` or `会計済み確認` because the confirm button uses a generic label.
- A backdrop click closes a destructive or external operation confirmation without explicit cancel intent.
- A future flow reuses the modal but omits the operation name, making audit/troubleshooting ambiguous.

## Implementation
- Added shared `CriticalOperationConfirmDialog` using `FocusTrapDialog` with `role=alertdialog`, no backdrop-close, explicit operation label, repeated patient fields, summary fields, and distinct confirm label.
- Replaced the Charts low-level ORCA send confirmation body with the shared modal.
- Changed the ORCA send confirm CTA from generic `送信する` to `ORCAへ送信する`.
- Updated focused tests for patient identifier repetition, distinct operation labeling, no backdrop cancel, and existing ORCA send behavior.
- Updated `web-client/notes/ui-current-contract.md` and this workstream evidence.

## Residual Risk
- This heartbeat applies the shared modal to Charts ORCA send only. Chart finalize, prescription finalize/cancel, disease ORCA send, billing/recovery, and diagnosis send confirmations still need staged adoption.

## Scope

One-heartbeat slice for checklist 11 / Phase 4: move `DiagnosisEditPanel` disease ORCA send confirmations onto the common critical-operation modal. This covers disease create/update/delete/organize-deleted confirmation UI only. Server-side authorization, request-number ownership, ORCA mutation semantics, persistence, and audit enforcement remain backend-owned and are not treated as satisfied by UI controls.

## Assets, Trust Boundary, Attack Surface

- Assets: selected ORCA patient number, visit date, department code, insurance combination number, disease name/code/components, disease attributes, target disease for update/delete, pending action state, and post-mutation ORCA mirror status.
- Trust boundary: browser form state, route/query state, pending action state, and UI confirmation summaries are untrusted. The server remains authoritative for user/facility authorization, `diseasev3` request semantics, ORCA request number, official response classification, re-fetch, persistence, and audit.
- Attack surface: wrong-patient disease mutation, ambiguous disease create/update/delete labels, form-state changes being mistaken for confirmed server authority, ORCA accepted response being shown as registered without re-fetch, and tracked evidence leaking credentials/raw ORCA body/PHI/HAR/trace/video/screenshot.

## Misuse Cases

1. A user sends a disease mutation for the wrong patient because the old custom dialog does not follow the shared patient-identification pattern. Mitigation: `CriticalOperationConfirmDialog` now repeats ORCA patient number, visit date, department, insurance combination, operation, and disease summary in an `alertdialog`.
2. A client mutates form state or tampers pending action values after opening confirmation and treats the UI summary as authoritative. Mitigation: the UI only snapshots and confirms intent; docs explicitly keep authorization, request-number ownership, persistence, and audit enforcement on the server.
3. A disease ORCA send is confused with chart finalization, accounting, or generic ORCA send. Mitigation: the modal operation is `病名ORCA送信`, title is each disease operation confirmation, and confirm CTAs remain `ORCAへ病名登録` / `ORCA病名を更新` / `ORCA病名を削除` / `削除病名を整理`.
4. A blocked or pending disease operation proceeds from a confirmation surface. Mitigation: existing `isOrcaMutationBlocked` and `isAnyMutationPending` guards are retained; the common modal now supports disabled cancel/confirm buttons for pending and blocked states.

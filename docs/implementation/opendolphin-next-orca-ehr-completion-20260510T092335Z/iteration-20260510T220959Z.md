## Assets / Trust Boundary / Attack Surface

- Assets: `prescription_order`, `prescription_order_revision`, `orca_medical_candidate`, candidate JSON, issue summary, audit event metadata.
- Trust boundary: browser path only supplies `chartRevisionId`; facility and actor come from authenticated server context; patient / encounter / prescription revision are resolved from DB.
- Attack surface: `POST /api/local/orca/medical-candidates/from-chart/{chartRevisionId}` and direct DB access to candidate rows.

## Misuse Cases

- Client tries to pass patient / facility / insurance / voucher / sequential values to create a candidate for another patient.
- Client hides unresolved drug or usage codes and attempts to make the candidate sendable.
- Client mistakes a candidate for ORCA source-of-truth medical data.
- Audit write path is down and candidate creation proceeds without traceability.

## Implementation

- Added `orca_medical_candidate` migration with candidate status, sendable flag, source system, candidate JSON, and issue summary.
- Added `POST /api/local/orca/medical-candidates/from-chart/{chartRevisionId}`.
- Candidate is built from current prescription revision summary by chart revision and facility; no live `medicalmodv2` send is performed.
- Missing medical class, usage code, drug code, or medication rows become `NEEDS_REVIEW` / `sendable=false`.
- Added response DTO and focused resource tests.

# Worker D Iteration 20260511T004209Z

## Scope
- Worker D D-04 follow-up: report fetch pipeline wiring.
- Checklist 10.3 / 10.4: ORCA report snapshots remain ORCA-derived evidence, and binary staging uses only server-side storage authority.

## Implementation
- Changed `OrcaBillingCacheStore.saveReportSnapshot` to return a `ReportSnapshotReceipt` containing the DB snapshot id, facility, snapshot status, server-generated object key/digest, upload status, and upload eligibility.
- Wired `OrcaReportDocumentResource` to call `OrcaReportBinaryStorageService` after snapshot persistence when object storage upload is enabled and the snapshot is eligible.
- Added safe response fields to `OrcaReportResponse`: `storageUploadStatus` and `reportBinaryAvailable`. The public response still does not expose storage URI, object key, digest, bucket, raw Data_Id, invoice number, or report body.
- Added resource tests for enabled upload success and enabled upload failure. Enabled upload failure returns HTTP 503 instead of reporting the ORCA report fetch as successful.
- Updated ORCA connection contract, checklist, worker-board, and this iteration record.

## Threats / Mitigations
- Misuse case 1: A client supplies storage key/digest/retention values to control report object placement. Mitigation: the public request has no storage fields; upload command is built from the DB snapshot receipt and transport response.
- Misuse case 2: Object storage fails after ORCA returns a valid report response, leaving the UI believing a binary is available. Mitigation: when upload is enabled and fails, the resource returns HTTP 503 and records a sanitized failure audit action.
- Misuse case 3: Response or audit leaks object key, digest, raw invoice, raw Data_Id, or report body. Mitigation: response exposes only `storageUploadStatus` and `reportBinaryAvailable`; audit details use report type, snapshot id, upload status, retention timestamp, and fixed reason code.

## Scope

One-heartbeat slice for checklist 11 / Phase 4: add the common critical-operation confirmation to `PrescriptionOrderEditorPanel` for `処方確定`. This is a UI confirmation and client API sequencing change only. Prescription finalize authorization, status transition, content hash, persistence, and audit enforcement remain server-side prescription workflow responsibilities.

## Assets, Trust Boundary, Attack Surface

- Assets: prescription RP/drug rows, patient ID, encounter ID, visit date, chart revision reference, finalize intent, and server-returned prescription ID/revision/status/content hash.
- Trust boundary: browser state, editor values, selected encounter, validation state, button state, and modal text are untrusted UI hints. The server remains authoritative for prescription identity, finalize permission, status transition, content hash, and audit.
- Attack surface: wrong-patient prescription finalize, save/finalize confusion, client-supplied prescription identity tampering, and empty or invalid prescription submission.

## Misuse Cases

1. A user finalizes a prescription while viewing the wrong patient or encounter. Mitigation: the common alertdialog repeats patient ID, visit date, encounter reference, RP/drug counts, and start date before execution.
2. A user mistakes `保存` for `処方確定`, or treats a local UI success as ORCA/accounting completion. Mitigation: `処方確定` is a distinct danger action with a distinct confirm CTA and the modal states `ORCA送信や会計済み確定ではありません`.
3. A malicious client attempts to finalize an arbitrary prescription ID. Mitigation: the client draft request does not accept a preselected prescription ID for finalize; it calls finalize only with the server-returned `prescriptionId`. Server-side authorization and ownership enforcement remain required.
4. A user attempts to finalize an invalid or empty prescription. Mitigation: existing editor validation runs before the confirmation opens, and the focused UI test verifies the API is not called before confirm.

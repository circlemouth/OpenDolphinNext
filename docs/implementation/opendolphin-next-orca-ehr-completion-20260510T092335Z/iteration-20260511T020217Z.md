## Scope

Persist a sanitized candidate snapshot that carries the server-generated prescription content hash without turning browser-held patient, encounter, insurance, voucher, or sequential values into authority. This iteration does not implement live `medicalmodv2` send, ORCA re-fetch, or reconciliation.

## Assets And Trust Boundary

- Assets: `orca_medical_candidate.candidate_json`, prescription content hash, candidate medical information rows.
- Authority: candidate metadata and rows are generated server-side from prescription source-of-truth.
- Untrusted inputs: client patient, encounter, facility, insurance, voucher, sequential, URL, digest, owner, and role values.

## Misuse Cases

- A downstream workflow reads `candidate_json` and mistakenly treats embedded patient or insurance values as authority.
- A client-influenced voucher or sequential number is persisted in the candidate snapshot and later reused for ORCA send.
- A candidate loses the prescription content hash when persisted, making later send/re-fetch/diff binding ambiguous.

## Implementation

- Changed `OrcaMedicalCandidateRepository` so `candidate_json` stores a sanitized snapshot with:
  - `nonAuthoritative`
  - `candidateStatus`
  - `sendable`
  - `prescriptionContentHash`
  - `medicalInformation`
- Added a focused repository test proving the snapshot excludes patient / encounter / insurance / voucher / sequential authority fields.
- Updated `docs/contracts/prescription-authority.md` to make the persisted candidate snapshot boundary explicit.

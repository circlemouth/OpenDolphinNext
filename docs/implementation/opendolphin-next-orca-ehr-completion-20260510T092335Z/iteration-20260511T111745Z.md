## Scope

One-heartbeat slice for checklist 11 / Phase 4: extend the common medical-safety patient header into the Reception existing-patient accept workflow modal. This is UI patient-identification support only; server-side authorization, ORCA acceptance, and persistence enforcement remain backend-owned.

## Assets, Trust Boundary, Attack Surface

- Assets: selected Reception patient identity, reception date, department, physician, payment/insurance context, ORCA accept-target readiness status, and row-local handoff references.
- Trust boundary: browser state, form values, search filters, selected cards, and modal state are untrusted client context. Server-side APIs remain authoritative for ORCA official lookup, acceptance, authorization, and persistence.
- Attack surface: wrong-patient selection, stale or tampered department/physician/payment state, misleading ORCA registration wording, accidental PHI/credential/raw ORCA evidence in tracked docs/tests, and accessible-name regressions in the accept modal.

## Misuse Cases

1. A user selects the wrong search result and proceeds because the form only shows department/payment controls. Mitigation: the accept panel now repeats a common `PatientIdentityBar` before controls with patient ID, name/kana, reception date, department, physician, payment context, and ORCA readiness.
2. A client tampers department, physician, or payment mode and treats the UI as an authority source. Mitigation: the UI only displays the selected context and keeps wording to `ORCA受付対象確認`; it does not add persistence or authorization claims.
3. Insurance is auto-selected but the ORCA insurance combination number is not available. Mitigation: the header displays `保険（組合せ未確定）` instead of fabricating an ORCA combination number.
4. Evidence files or tests leak raw ORCA bodies, credentials, or PHI. Mitigation: no raw ORCA payloads, credentials, HAR, trace, video, or screenshot artifacts were added; tests use existing synthetic names/IDs.

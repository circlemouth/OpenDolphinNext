# Worker A Iteration 20260510T233304Z

## Scope

- Queue: A-06 patientgetv2 cache write failure behavior.
- Checklist: 3.1, 6, 13.
- Assets: official `patientgetv2` response, `orca_patient_cache`, patientget audit details, source metadata response headers.
- Trust boundary: live ORCA response plus successful server-side cache write are required before returning a current-source success response. Client input and old local cache are not authority.
- Attack surface: masking cache write failure as a successful live ORCA response, promoting stale cache as current, leaking raw ORCA body or patient detail in failure audit.

## Misuse Cases

- Cache storage fails after ORCA transport succeeds and the wrapper still returns `X-Orca-Stale=false` success.
- Old patient cache is treated as current ORCA source after a write failure.
- Failure audit records raw ORCA body, credentials, or patient detail.
- Facility cannot be resolved but another facility's patient cache is used.

## Implementation

- Added focused `OrcaPatientApiResourceRunIdTest` coverage that forces `orca_patient_cache` write failure.
- Verified failure path records sanitized failure audit and does not attach success-only source/cache/stale metadata.
- Updated ORCA connection and route taxonomy contracts to state that patientgetv2 cache write failure must not return current-source success.
- Marked patient cache metadata and cache-write-failure checklist items complete.
- Updated Worker A board entry.

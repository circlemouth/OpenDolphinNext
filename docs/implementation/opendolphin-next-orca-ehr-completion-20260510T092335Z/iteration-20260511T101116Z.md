## Threat Model

Assets:

- `prescription_order_event` and `prescription_order_revision` history.
- `orca_medical_candidate.candidate_json` handoff payload.
- disease mutation DTOs used by server-side diseasev3 handoff.
- chart export/reporting integration points owned by Worker B.

Trust boundary:

- Browser and API request payloads are untrusted.
- Prescription history must be read from DB rows scoped by authenticated facility and prescription order id.
- Disease DTO completeness does not make client-provided facility, request number, URL, raw XML, voucher, sequential, or insurance values authoritative.

Attack surface:

- Candidate prepare/latest JSON returned to web-client and later export/reporting integration.
- `DiseaseMutationRequest` JSON deserialization.
- Audit/iteration docs that could accidentally record raw ORCA body or PHI.

Misuse cases:

- Client injects patient/facility/voucher/sequential/digest in candidate request and later workflow treats it as authority.
- Export integration reads raw prescription before/after summary JSON and leaks PHI, raw ORCA XML, credential, or insurance details.
- Old candidate is reused after change/reissue/cancel and appears sendable without source revision/hash verification.
- Disease mutation payload omits physician / base month / receipt / insurance disease fields, forcing downstream code to infer from display text.

Countermeasures:

- Candidate request path remains `chartRevisionId` only; no body/query authority fields were added.
- `prescriptionHistory` snapshot is built server-side from DB allowlist fields only and stored inside sanitized `candidate_json`.
- Free-text history fields are redacted for Authorization, Cookie, raw XML, and SOAP body before response/snapshot.
- Latest candidate still compares saved prescription order/revision/hash/status to current DB state and marks stale candidates `NEEDS_REVIEW`.
- `DiseaseMutationRequestContractTest` fixes field completeness in a deserialization contract test.

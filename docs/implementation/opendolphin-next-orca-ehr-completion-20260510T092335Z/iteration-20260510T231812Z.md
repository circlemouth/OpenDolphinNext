# Worker D Iteration 20260510T231812Z

## Scope
- Worker D D-04 follow-up: report storage authority.
- Checklist 10.3 / 10.4: receipt/report data as ORCA-derived snapshot with server-side storage metadata.

## Implementation
- `OrcaBillingCacheStore.saveReportSnapshot` now fills `server_storage_object_key` and `server_storage_digest`.
- The storage key is server-generated from facility hash, report type, request hash, and response hash.
- The storage digest is the server-calculated response hash. Client-provided storage key/digest/path/URI is not accepted by the command or public report API.
- Updated ORCA connection contract and outage recovery runbook to make server-generated report storage metadata the authority.

## Threats / Mitigations
- Misuse case 1: A client supplies a storage key/path to overwrite or reference arbitrary report objects. Mitigation: report API and store command do not accept client storage key/digest.
- Misuse case 2: Raw patient ID, invoice number, or ORCA Data_Id leaks into object keys. Mitigation: keys use facility hash plus request/response hashes; focused tests assert raw values are absent.
- Misuse case 3: Restore uses a locally invented report path as evidence. Mitigation: runbook now requires server-generated `server_storage_object_key` / `server_storage_digest` and marks mismatches as `NEEDS_REVIEW`.

## Scope

One-heartbeat slice for checklist 11 / Phase 4: move the chart revision drawer's revise/restore confirmation onto the common `CriticalOperationConfirmDialog`. This covers UI confirmation only. Chart revision authorization, append-only events, content hash, persistence, and audit enforcement remain server-side / owning workflow responsibilities.

## Assets, Trust Boundary, Attack Surface

- Assets: selected patient ID, visit date, reception/appointment references, target revision ID, parent revision ID, revision authored time, revise/restore intent, and revision write API invocation.
- Trust boundary: browser state, revision list rendering, confirm dialog content, and button state are untrusted UI hints. Server-side chart revision workflow remains authoritative for permissions, append-only persistence, hash validation, and audit.
- Attack surface: wrong-patient revision write, wrong revision selected for correction/restore, accidental restore/overwrite-like action, and UI confirmation being mistaken for authorization or immutable event enforcement.

## Misuse Cases

1. A user clicks revise/restore on the wrong patient's revision because the drawer list alone is not enough context. Mitigation: common alertdialog repeats patient ID, visit date, reception ID, appointment ID, and target revision before calling the write API.
2. A user accidentally executes a revision write while intending only to inspect history. Mitigation: revise/restore now requires the shared critical-operation confirm; the focused test asserts the API is not called before confirmation.
3. A stale or unexpected parent revision is acted on without review. Mitigation: the confirm summary shows target revision and parent revision; server-side conflict and append-only enforcement remain authoritative.
4. The UI confirm is treated as permission enforcement. Mitigation: current contract and iteration notes explicitly keep authorization, persistence, content hash, and audit on the server-side chart revision workflow.

## Scope

This iteration closed the Web client half of the diseasev3 readback contract introduced by the prior server iteration. Charts now treats `postMutationMirrorStatus=connected` + `postMutationMirror` as the only immediate source for ORCA registered disease list updates after create/update/delete/organize operations.

## Changes

- Added `postMutationMirrorStatus` and normalized `postMutationMirror` to the `mutateOrcaDisease` client result.
- Updated `DiagnosisEditPanel` to apply connected post-mutation mirrors directly into the `charts-diagnosis` query cache.
- Kept accepted-but-unrefetched disease mutations out of the registered list and surfaced them as warning / review-required copy.
- Added focused tests for connected mirror replacement, unavailable mirror review copy, and API normalization.
- Updated the disease ORCA contract and implementation checklist with the Web client readback behavior.

## Threats And Mitigations

- Threat: UI could show user-entered disease text as registered even when ORCA re-fetch failed.
  Mitigation: the panel only updates the registered list from `postMutationMirror`; unavailable mirror responses show warning copy and keep the old mirror.
- Threat: diseasev3 accepted responses could be confused with source-of-truth confirmation.
  Mitigation: accepted-but-unavailable responses remain `ok=false` / warning in the client result.
- Threat: stale query invalidation could refetch and mask whether the immediate list came from server readback.
  Mitigation: connected post-mutation mirrors are applied with `setQueryData`; unavailable mirrors are not invalidated into optimistic success.

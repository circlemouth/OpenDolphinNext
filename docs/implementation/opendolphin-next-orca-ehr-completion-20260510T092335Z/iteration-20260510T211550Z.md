## Selected Task

D-02 was selected because D-01 was already recorded as done on the worker board. This iteration adds the shared ORCA operation ledger schema that later medical/billing/report adapters can use without storing raw ORCA bodies or credentials.

## Assets / Trust Boundary / Attack Surface

- Assets: ORCA operation status, idempotency key, request/response hash, sanitized warning/unmatched/error summary, post-send reconciliation result, retry metadata.
- Trust boundary: Browser payload and ORCA external response are untrusted. Server-side authenticated facility, server-derived encounter/snapshot context, and adapter-normalized summaries are the only authorities for persisted operation context.
- Attack surface: tampered client facility/context, duplicated operation submission, raw body or credential leakage through DB/evidence, ambiguous ORCA success classification, unsafe resend after `UNKNOWN`.

## Misuse Cases

1. A client sends forged facility, voucher, sequential, insurance combination, or `Medical_Uid` to make another facility's ORCA operation appear sendable.
2. A transport failure or parser ambiguity is collapsed into success, allowing a user to treat `UNKNOWN` as ORCA accepted.
3. Raw XML, credentials, patient details, or ORCA identifiers are stored in operation evidence and later leak through reviewer packets or logs.
4. A duplicate idempotency key is replayed to create multiple ORCA transmissions for the same server-derived request.

## Scope

Harden latest `orca_medical_candidate` preview binding so it is compared with the current prescription source for the chart revision, not only with the candidate's saved prescription order. This iteration does not implement live `medicalmodv2` send, ORCA adapter behavior, post-send re-fetch, or reconciliation.

## Threat Model

- Assets: `orca_medical_candidate` snapshot, current chart revision prescription order, source prescription revision id, prescription content hash.
- Trust boundary: client provides only the chart revision route segment; facility and current prescription source are resolved server-side.
- Attack surface: latest candidate preview response and downstream send-preparation display.

Misuse cases:

- A new prescription order is created for the same chart revision, but an older candidate tied to a previous order still appears sendable.
- Client attempts to rely on stale candidate/order identity instead of the chart revision's current prescription source.
- Current chart revision no longer has a matching prescription source, but latest candidate preview remains sendable.

## Changes

- Changed latest candidate lookup to resolve the current prescription order/revision for the facility/chart revision with the same ordering used by candidate preparation.
- Marked latest candidate preview stale when saved `prescription_order_id`, saved revision id, or saved hash differs from the current chart prescription source.
- Updated prescription authority, route taxonomy, and UI current contract docs.

## Assets / Trust Boundary / Attack Surface

- Assets: prescription-derived `orca_medical_candidate`, Charts patient/acceptance display context, candidate status/issues.
- Trust boundary: browser display context is non-authoritative; candidate prepare request sends only `chartRevisionId`; server resolves facility/patient/encounter/prescription revision.
- Attack surface: Charts candidate prepare button and `/api/local/orca/medical-candidates/from-chart/{chartRevisionId}` API call.

## Misuse Cases

- Client tries to include facility, patient, insurance, voucher, sequential, URL, digest, or role in candidate prepare payload.
- User mistakes candidate preparation for live ORCA `medicalmodv2` send or ORCA source-of-truth registration.
- Missing chart revision still triggers a network call and leaks display-only encounter context.
- Candidate issue list is hidden, allowing unresolved usage/drug/medical class to look sendable.

## Implementation

- Added `orcaMedicalCandidateApi.ts` for local candidate preparation; request path contains only `chartRevisionId` and no request body.
- Added `OrcaMedicalCandidatePanel` to show patient, acceptance, department, physician, insurance, candidate status, row counts, and unresolved issues.
- Integrated the panel into `ChartsActionBar`; it fails closed when `chartRevisionId` is absent and does not expose a live send button.
- Extended volatile encounter context with optional `chartRevisionId` for future chart revision handoff without URL/storage authority.

## Scope

Harden the read-only latest `orca_medical_candidate` preview so a previously prepared candidate cannot appear sendable after the underlying prescription source changed. This iteration does not implement live `medicalmodv2` send, ORCA adapter behavior, post-send re-fetch, or reconciliation.

## Threat Model

- Assets: `orca_medical_candidate` snapshot, current prescription revision hash, candidate sendability signal.
- Trust boundary: client can name only the chart revision path segment; facility and current prescription state are resolved server-side.
- Attack surface: `GET /api/local/orca/medical-candidates/from-chart/{chartRevisionId}/latest`.

Misuse cases:

- Client reuses an older latest candidate after a prescription change/reissue and treats it as current.
- Client sends fake digest or authority fields to convince the UI or later send workflow that the candidate still matches the current prescription.
- Candidate preview returns `sendable=true` even though the current prescription revision hash no longer matches the saved candidate snapshot.

## Changes

- Joined latest candidate lookup to the current prescription order/revision hash.
- Compared saved candidate `prescriptionContentHash` with current prescription revision `content_hash` server-side.
- Marked stale latest candidates as `NEEDS_REVIEW`, `sendable=false`, with `prescription_candidate_source_stale`.
- Updated prescription authority, route taxonomy, and UI current contract docs.

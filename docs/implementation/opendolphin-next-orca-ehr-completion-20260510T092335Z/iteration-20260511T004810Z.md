## Assets / trust boundary / attack surface
- Assets: `chart_revision.snapshot_manifest_json`, finalize content hash material, JSON/CSV export snapshot summary, reporting summary allowlist.
- Trust boundary: finalize request JSON is client-controlled; snapshot manifest must be generated from server-side validated finalize context only.
- Attack surface: client-provided patient/insurance detail injection, raw ORCA body leakage through snapshot/export, formula injection in CSV summary.

## Misuse cases
- A client attempts to submit patient name, phone, insurance detail, or raw ORCA response as a snapshot field.
- A caller tries to include Authorization/Cookie/XML text in snapshot/export fields to leak credentials or raw transport bodies.
- A CSV consumer opens exported revision history containing formula-leading snapshot values.

## Implementation
- Added migration `V0321__chart_revision_snapshot_manifest.sql` and `ChartRevisionModel.snapshotManifestJson`.
- `ChartRevisionFinalizeService` now writes a server-generated snapshot manifest skeleton from validated ORCA patient id, encounter, acceptance/no-acceptance reason, department, physician, and insurance combination.
- Snapshot manifest is included in content hash material, so later tampering changes the chart revision hash.
- JSON/CSV export projects snapshot manifest through an explicit allowlist and redaction path; unsafe patient/raw ORCA keys are dropped.
- Reporting event summary allowlist now permits `hasSnapshotManifest` only as a scalar provenance flag.

## Scope

Candidate prepare remains a local, non-authoritative handoff from prescription source-of-truth to the later ORCA `medicalmodv2` workflow. This iteration does not implement live send, adapter behavior, re-fetch, or reconciliation.

## Assets And Trust Boundary

- Assets: `prescription_order`, `prescription_order_revision`, `orca_medical_candidate`, candidate response DTO, append-only audit event.
- Authority: facility and actor from authenticated request context; patient / encounter / prescription revision from DB rows.
- Untrusted inputs: browser route path, any client-held patient / encounter / facility / insurance / voucher / sequential / digest / URL, and decoded JSON summary if it disagrees with the authoritative order row.

## Misuse Cases

- A stale or corrupted revision summary contains a different patient ID than the current `prescription_order` row and is prepared as a send candidate.
- A summary from another encounter is attached to the same chart revision and produces a candidate that later live-send code could treat as valid.
- A client tries to use candidate preparation as a bridge to inject cross-patient context without sending an explicit request body.

## Implementation

- Added a server-side summary authority check in `LocalOrcaMedicalCandidateResource`.
- Candidate preparation now rejects mismatched or missing summary patient / encounter context with `prescription_source_context_mismatch` before persistence.
- Added focused regression coverage that verifies mismatched summary context returns 409 and does not save a candidate.

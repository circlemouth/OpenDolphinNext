## Scope

Harden latest `orca_medical_candidate` preview so a candidate is not sendable when the current chart prescription source has moved to a non-sendable prescription status. This iteration does not implement live `medicalmodv2` send, ORCA adapter behavior, post-send re-fetch, or reconciliation.

## Threat Model

- Assets: `orca_medical_candidate` snapshot, current chart revision prescription order status, source prescription revision id, prescription content hash.
- Trust boundary: client provides only the chart revision route segment; facility and current prescription source/status are resolved server-side.
- Attack surface: latest candidate preview response and downstream send-preparation display.

Misuse cases:

- A prescription is cancelled or stopped after candidate creation, but the old candidate still appears sendable.
- Client attempts to rely on stale candidate status instead of the current prescription source status.
- Current chart revision source is missing or non-final, but latest candidate preview remains sendable because order/revision/hash still match.

## Changes

- Added current prescription status to latest candidate lookup.
- Marked latest candidate preview stale when current status is not `FINAL`, `CHANGED`, or `REISSUED`.
- Kept existing current order id, revision id, and content hash comparisons.
- Updated prescription authority, route taxonomy, and UI current contract docs.

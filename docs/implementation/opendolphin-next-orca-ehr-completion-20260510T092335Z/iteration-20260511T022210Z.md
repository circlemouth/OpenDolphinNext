## Scope

Add a read-only latest candidate confirmation path for prescription-derived `orca_medical_candidate` rows. This iteration does not create a new candidate, implement live `medicalmodv2` send, call an ORCA adapter, or mark an ORCA workflow complete.

## Threat Model

- Assets: `orca_medical_candidate` DB rows, sanitized candidate snapshot, prescription content hash, RP/item row identity.
- Trust boundary: client may provide only `chartRevisionId` in the route path; facility and actor context stay server-side.
- Attack surface: `GET /api/local/orca/medical-candidates/from-chart/{chartRevisionId}/latest` and the Charts API client wrapper.

Misuse cases:

- Client attempts to fetch a candidate for another facility by providing patient/facility/insurance/voucher/sequential fields in request payload.
- Client attempts to bind a candidate to a fake digest or arbitrary URL/storage key.
- Saved candidate snapshot accidentally carries derived or authority-looking fields into later send/re-fetch workflows.

- Added `GET /api/local/orca/medical-candidates/from-chart/{chartRevisionId}/latest`.
- Rebuilt latest candidate responses from server-owned DB row fields plus sanitized snapshot/issue summary.

## Assets

- `prescription_order`, `prescription_order_revision`, `prescription_order_item`, `prescription_order_event`, `prescription_orca_transmission`
- Server-side prescription authority and later ORCA medical candidate preparation
- Sanitized contract docs only; no raw ORCA body, patient detail, credential, HAR, trace, video, or screenshot evidence

## Trust Boundary

- Browser payload is untrusted for facility, owner, role, voucher, sequential, insurance combination, storage key, digest, URL, and ORCA identifiers.
- DB status and future server-side authority APIs decide whether a prescription can move out of `DRAFT`.
- Event history is append-only and is not editable by client payload.

## Attack Surface

- Direct SQL or future repository code attempting to overwrite a finalized prescription row.
- Local draft/DO import payload paths trying to bypass revision/event history.
- ORCA candidate preparation using JSON-only payloads without structured item resolution.

## Misuse Cases

- A client tampers with `patient_id` or item dosage after a prescription is already `FINAL`.
- A client deletes or edits `prescription_order_event` rows to erase stop/cancel/change history.
- A stale browser tab tries to insert or update prescription items after the order moved to `FINAL`.
- A malicious payload supplies voucher/sequential/insurance values and expects them to become send authority.

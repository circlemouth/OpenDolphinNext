## Trust Boundary
- Client retry intent and idempotency keys are not authority to send ORCA billing for an encounter that is already closed for billing.
- Server-side `encounter_projection.business_state` decides whether a new normal billing send may proceed.
- Existing same-idempotency transmission records remain read-only replay results and are not converted into new ORCA sends.

## Attack Surface
- Reusing a new idempotency key to send `medicalmodv2 class=01` again after the encounter has entered `accounting-wait`.
- Closed or billed encounter state reaching patient lookup, karte lookup, snapshot mutation, or ORCA transport.
- Failure evidence exposing raw ORCA body, credentials, patient details, or insurance details.

## Misuse Cases
1. A user resubmits an already accounting-wait encounter with a fresh idempotency key to create a duplicate ORCA billing send.
2. A closed or billed encounter is sent again because only `cancelled` was blocked.
3. An existing idempotency result is mistaken for permission to create a new ORCA transmission.
4. A blocked send leaks raw ORCA or patient/insurance details into tracked evidence.

## Implementation
- Normal billing send now checks for existing same-idempotency transmission before closed-state blocking and returns the stored result when present.
- New sends fail closed with `encounter_billing_send_blocked` for `accounting-wait`, `billing-waiting`, `billed`, `closed`, `chart-finalized`, `orca-sent`, and ORCA-medical-registered state aliases.
- The guard runs before patient lookup, karte lookup, snapshot upsert, or ORCA transport.

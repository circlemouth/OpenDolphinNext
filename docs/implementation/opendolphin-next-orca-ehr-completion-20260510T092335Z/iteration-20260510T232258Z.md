# Worker D Iteration 20260510T232258Z

## Scope
- Worker D D-04 follow-up: report binary upload / retention gate.
- Checklist 10.3 / 10.4: ORCA report snapshots remain ORCA-derived evidence and do not expose usable binary objects unless storage metadata is complete.

## Implementation
- Added `V0320__orca_report_storage_gate.sql` for `orca_report_snapshot.storage_upload_status`, `storage_uploaded_at`, and `storage_retention_until`.
- Added DB constraints so `UPLOADED` / `RETENTION_BLOCKED` snapshots require server-generated object key, server-generated digest, upload time, and retention-until metadata.
- `OrcaBillingCacheStore.saveReportSnapshot` marks normal report fetch history as `NOT_UPLOADED` and includes sanitized binary availability / retention status in `summary_json`.
- Updated ORCA connection contract and outage recovery runbook to forbid binary reuse when upload or retention metadata is incomplete.

## Threats / Mitigations
- Misuse case 1: A report snapshot is treated as a usable binary object even though no object was uploaded. Mitigation: default status is `NOT_UPLOADED`, and summary marks `reportBinaryAvailable=false`.
- Misuse case 2: A future uploader marks a binary as `UPLOADED` without server-generated key/digest. Mitigation: DB constraint rejects `UPLOADED` / `RETENTION_BLOCKED` rows missing key/digest.
- Misuse case 3: Restore flow reuses a stale or retention-unknown report binary. Mitigation: runbook requires `storage_uploaded_at` and `storage_retention_until`; missing metadata means re-fetch from ORCA.
